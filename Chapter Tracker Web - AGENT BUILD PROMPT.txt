The current project is a Python standard-library GitHub Action. It:

- checks weebcentral's One Piece RSS feed 5 times a day;
- compares the latest chapter with state/last_chapter.json;
- sends a Discord embed to one or two webhooks;
- optionally pings a role on webhook 2 using DISCORD_ROLE_ID_2;

  CHAPTER_NUM_RE = /Chapter\s+(\d+(?:\.\d+)?)/i

Discord payload behavior in the reference:

  - embed title: chapter title (or "One Piece Chapter N")
  - embed url: chapter URL
  - description: "A new One Piece chapter is out."
  - color: orange (0xE67E22)
  - timestamp: current UTC time
  - footer: "weebcentral"

3. PRODUCT REQUIREMENTS
--------------------------------------------------------------------------------

3.1 Authentication

- Discord OAuth only for v1. No passwords, no email magic links, no GitHub login.
- Users already need Discord to receive alerts, so Discord login is the natural
  identity.
- Use Discord OAuth scopes `identify`. Do not request bot permissions.
- Store Discord user ID, display name, and avatar URL through Better Auth.
- Sign out must invalidate the session.
- If OAuth fails, show a clear error and a retry path; do not dump provider
  errors containing secrets.
- Account deletion must be available in Settings with an explicit confirmation.

3.2 Series

- A user can add multiple series. Defaults:
    MAX_SERIES_PER_USER = 5
    MAX_ACTIVE_SERIES = 150 globally
- The user adds a series by pasting a weebcentral series link, for example:
    https://weebcentral.com/series/01J76XY7E9FNDZ1DBBM6PBJPFK/One-Piece
- The server must derive the RSS feed:
    https://weebcentral.com/series/<id>/rss
- The server must fetch and validate the feed before saving.
- Show a preview: series title, latest chapter number, latest chapter title,
  latest chapter link, and whether the series is already tracked.
- If the series is already globally tracked, adding it must reuse the existing
  series row and not cause another feed poll.
- Each subscription belongs to exactly one destination in v1. A user can have
  multiple destinations and route different series to different destinations.
- Pause/resume and remove subscription.
- No backfill when adding a series. The first alert is the next newly detected
  chapter. Optional "send latest now" can be a later feature, not v1.

3.3 Destinations

- A user can add multiple Discord webhook destinations. Defaults:
    MAX_DESTINATIONS_PER_USER = 2
- Fields:
    label (user-facing, e.g. "One Piece channel")
    webhook URL (secret, write-only)
    optional role ID
- On save, the server GETs the Discord webhook to verify it exists and to read
  its name/channel/guild metadata. This sends no message.
- The full webhook URL must never be returned to the browser after save. Show
  the label, the channel/guild name, and "Webhook configured".
- A user can replace a webhook URL. Replacement re-verifies it and resets any
  failure/disabled state.
- A user can test a destination. Test sends go through the real POST path,
  are marked "[TEST]", and never touch chapter or delivery state.
- A destination can be deleted only if no active subscription uses it. If it is
  in use, return 409 and tell the user to reassign those series first.
- If Discord returns 401/403/404, mark the destination `disabled`, stop
  retrying it, and show a banner/status in the UI. Do not delete it silently.
- If the user re-tests or replaces the URL and it succeeds, re-enable it.

3.4 Alerts

- Post a Discord embed with:
    title: series title + chapter label (or the RSS item title)
    url: chapter link
    description: "A new chapter of <series> is out."
    color: vermilion/orange
    timestamp: current UTC time
    footer: "Chapter Tracker"
- If role ID configured:
    content: "<@&ROLE_ID>"
    allowed_mentions: { "parse": [], "roles": ["ROLE_ID"] }
  otherwise omit both fields.
- One message per chapter per destination. The delivery table's unique
  constraint is the last line of defense.
- If a webhook fails transiently, retry it later. Do not re-send to destinations
  that already succeeded.
- If a webhook is permanently dead, disable it and surface it in the UI.
- Do not claim "exactly once" in docs. Discord webhooks do not support
  idempotency keys. The design gives at-most-one normal notification and may
  duplicate only in the rare ambiguous success/timeout case. Document that.

3.5 Activity

- Show a delivery log for the signed-in user: series, chapter, destination
  label, status, timestamp, sanitized error.
- Statuses: queued, sent, retrying, failed, skipped/disabled.
- Limit to the most recent 50 by default; cursor pagination if easy.
- Never show full webhook URLs or role IDs to other users.
- Retain activity for 30 days, then prune via cron.

3.6 Free capacity / waitlist

- The product is free but capacity-capped.
- Count "active accounts" as users with at least one active subscription.
- If MAX_ACCOUNTS is reached, a new user can still sign in with Discord but
  cannot add their first series. Show a waitlist screen and store their Discord
  ID/username in a waitlist table.
- Existing users must not be evicted or degraded when the cap is reached.
- Show remaining capacity in the UI (e.g. "12 of 100 launch spots left") without
  exposing personal data.
- No automated invite system in v1. An operator can query D1/manual admin later.
- Default caps (all configurable by environment variables):
    MAX_ACCOUNTS = 100
    MAX_SERIES_PER_USER = 5
    MAX_DESTINATIONS_PER_USER = 2
    MAX_ACTIVE_SERIES = 150
    POLL_INTERVAL_MINUTES = 30
    CRON_BATCH_SERIES = 20
    CRON_BATCH_DELIVERIES = 20
    MAX_TEST_SENDS_PER_HOUR = 5
- The numbers are a starting budget for Cloudflare free. Do not raise them
  without a load test and a written capacity note.

3.7 Explicit non-goals for v1

- No Discord bot, no channel/role pickers, no Manage Webhooks permission.
- No manga sources other than weebcentral.
- No chapter content hosting or scraping beyond RSS metadata and links.

4. FREE-TIER BUDGET AND WHY THE LIMITS EXIST
--------------------------------------------------------------------------------

Cloudflare Workers Free (current limits to verify at build time):

- 100,000 Worker requests per day, account-wide, resetting 00:00 UTC.
- 10 ms CPU time per HTTP/Cron invocation on Free.
- 50 subrequests per invocation on Free.
- 5 Cron Triggers per account.
- Static asset requests are free and do not consume Worker requests.
- D1 Free: 5 million rows read/day, 100,000 rows written/day, 5 GB total.
- D1 queries per Worker invocation: 50 on Free.
- Exceeding a daily limit makes requests/queries fail until the reset.
- Workers Paid is $5/month, but this project must not require it.

Design consequences:

- The React frontend must be static assets. Do not do SSR.
- The API must be small and efficient. No heavy libraries or large payloads.
- Cron runs every 5 minutes; each series is due every POLL_INTERVAL_MINUTES
  with jitter. Do not poll all series at once.
- Each Cron invocation processes at most CRON_BATCH_SERIES feed fetches and
  CRON_BATCH_DELIVERIES sends. This keeps subrequests under 50 with headroom.
- If more series are due, leave them due for the next run. The effective check
  interval may stretch under load; this is better than failing.
- One feed poll is shared by every user subscribed to that series.
- No per-user polling. No per-user cron. No per-user webhook requests except
  explicit test sends.
- Use D1 batch operations where possible.
- Store only text/JSON; no images, cover art, or file storage.
- Cleanup old job_runs/activity rows in cron to keep D1 small.
- No Cloudflare Queues/Workflows/Durable Objects in v1 unless they are proven
  free and necessary. A D1 lock is enough to serialize cron runs.

Rough budget check to include in the README:

  150 series × 2 checks/hour = 300 feed checks/hour.
  At 20 series per 5-minute run, 240 checks/hour; under sustained maximum load
  the effective interval stretches to ~37.5 minutes. That is acceptable and
  must be visible in the UI ("next check" can be approximate).
  100 users × ~20 app requests/day = ~2,000 Worker requests/day.
  288 cron invocations/day.
  Feed checks and deliveries are subrequests, not necessarily daily Worker
  requests, but still count toward subrequest and D1 budgets.
  The true bottleneck to measure is CPU time and D1 queries/writes.

The agent must run a local synthetic load test with 100 users, 150 series, and
a batch of deliveries. If the free plan cannot handle the defaults, lower the
caps and document why. Do not quietly switch to paid.

7. DATA MODEL
--------------------------------------------------------------------------------

Use Drizzle with D1. Let Better Auth's CLI generate its own tables
(`user`, `session`, `account`, `verification`) rather than hand-writing them.
Then add the app tables below. Use text IDs from `crypto.randomUUID()` and
UTC ISO-8601 strings for app timestamps.

Enable and respect foreign keys. D1 is SQLite. Use `ON DELETE CASCADE` for
user-owned data. Use `ON DELETE RESTRICT` for destinations referenced by
subscriptions; the API must explain the conflict.

Suggested schema:

  series (
    id TEXT PRIMARY KEY,
    source TEXT NOT NULL DEFAULT 'weebcentral',
    external_id TEXT NOT NULL,
    title TEXT NOT NULL,
    feed_url TEXT NOT NULL,
    site_url TEXT NOT NULL,
    latest_chapter_number REAL,
    latest_chapter_label TEXT,
    latest_chapter_title TEXT,
    latest_chapter_url TEXT,
    latest_published_at TEXT,
    next_check_at TEXT NOT NULL,
    last_checked_at TEXT,
    last_error TEXT,
    etag TEXT,
    last_modified TEXT,
    active INTEGER NOT NULL DEFAULT 1,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    UNIQUE(source, external_id)
  );

  chapters (
    id TEXT PRIMARY KEY,
    series_id TEXT NOT NULL REFERENCES series(id) ON DELETE CASCADE,
    chapter_number REAL NOT NULL,
    chapter_label TEXT NOT NULL,
    title TEXT NOT NULL,
    url TEXT NOT NULL,
    published_at TEXT,
    discovered_at TEXT NOT NULL,
    UNIQUE(series_id, chapter_number)
  );

  destinations (
    id TEXT PRIMARY KEY,
    user_id TEXT NOT NULL REFERENCES user(id) ON DELETE CASCADE,
    label TEXT NOT NULL,
    webhook_ciphertext TEXT NOT NULL,
    webhook_iv TEXT NOT NULL,
    webhook_fingerprint TEXT NOT NULL,
    guild_id TEXT,
    guild_name TEXT,
    channel_id TEXT,
    channel_name TEXT,
    role_id TEXT,
    status TEXT NOT NULL DEFAULT 'active'
      CHECK(status IN ('active', 'disabled')),
    last_error TEXT,
    last_checked_at TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    UNIQUE(user_id, webhook_fingerprint)
  );

  subscriptions (
    id TEXT PRIMARY KEY,
    user_id TEXT NOT NULL REFERENCES user(id) ON DELETE CASCADE,
    series_id TEXT NOT NULL REFERENCES series(id) ON DELETE CASCADE,
    destination_id TEXT NOT NULL REFERENCES destinations(id) ON DELETE RESTRICT,
    active INTEGER NOT NULL DEFAULT 1,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    UNIQUE(user_id, series_id)
  );

  deliveries (
    id TEXT PRIMARY KEY,
    chapter_id TEXT NOT NULL REFERENCES chapters(id) ON DELETE CASCADE,
    destination_id TEXT NOT NULL REFERENCES destinations(id) ON DELETE CASCADE,
    status TEXT NOT NULL DEFAULT 'pending'
      CHECK(status IN ('pending', 'sent', 'retry', 'failed', 'skipped')),
    attempts INTEGER NOT NULL DEFAULT 0,
    next_attempt_at TEXT,
    last_error TEXT,
    sent_at TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    UNIQUE(chapter_id, destination_id)
  );

  waitlist (
    id TEXT PRIMARY KEY,
    discord_id TEXT NOT NULL,
    username TEXT NOT NULL,
    created_at TEXT NOT NULL,
    UNIQUE(discord_id)
  );

  job_locks (
    name TEXT PRIMARY KEY,
    locked_until TEXT NOT NULL
  );

  job_runs (
    id TEXT PRIMARY KEY,
    started_at TEXT NOT NULL,
    finished_at TEXT,
    status TEXT NOT NULL,
    feeds_checked INTEGER NOT NULL DEFAULT 0,
    chapters_found INTEGER NOT NULL DEFAULT 0,
    deliveries_sent INTEGER NOT NULL DEFAULT 0,
    errors INTEGER NOT NULL DEFAULT 0,
    detail TEXT
  );

  rate_limits (
    key TEXT PRIMARY KEY,
    window_start TEXT NOT NULL,
    count INTEGER NOT NULL
  );

Indexes:

  CREATE INDEX idx_series_due ON series(active, next_check_at);
  CREATE INDEX idx_subscriptions_user ON subscriptions(user_id);
  CREATE INDEX idx_subscriptions_series ON subscriptions(series_id);
  CREATE INDEX idx_destinations_user ON destinations(user_id);
  CREATE INDEX idx_chapters_series ON chapters(series_id, chapter_number);
  CREATE INDEX idx_deliveries_due ON deliveries(status, next_attempt_at);
  CREATE INDEX idx_deliveries_destination ON deliveries(destination_id);
  CREATE INDEX idx_job_runs_started ON job_runs(started_at);

Important:

- `series` is shared globally. Two users tracking One Piece must share one row.
- `subscriptions` is per user/series and points to one destination.
- `chapters` is shared globally and unique per series/number.
- `deliveries` is per chapter/destination and must be unique.
- A series should be polled only if at least one active subscription exists.
- Do not store webhook URLs in plaintext.
- Do not store role IDs in public/shared data. They are per-destination.
- App timestamps are UTC ISO strings; Better Auth may use integer timestamps;
  keep its schema as generated.
- Do not assume D1 supports interactive transactions. Use `db.batch`, unique
  constraints, and atomic UPDATE/INSERT patterns.
- Every query must include `WHERE user_id = ?` (or a verified join) for
  user-owned records.

Capacity queries:

  active accounts:
    SELECT COUNT(DISTINCT user_id) FROM subscriptions WHERE active = 1

  user series count:
    SELECT COUNT(*) FROM subscriptions WHERE user_id = ? AND active = 1

  user destination count:
    SELECT COUNT(*) FROM destinations WHERE user_id = ?

  global active series:
    SELECT COUNT(*) FROM series WHERE active = 1

Race conditions: use a D1 batch/atomic check or a unique constraint plus
verification. If two requests race to add the first subscription at the cap,
one must fail cleanly with CAPACITY_REACHED. Do not allow the cap to be
exceeded silently.

8. AUTHENTICATION
--------------------------------------------------------------------------------

Use Better Auth with the Discord provider. Follow its current Cloudflare/D1
guide; do not guess configuration.

Server setup:

- Create the auth instance per request with the Worker `env`.
- `baseURL` must come from `APP_URL`, never from the request Host header.
- `trustedOrigins` must include `APP_URL` and localhost in development.
- `secret` = `BETTER_AUTH_SECRET`.
- Sessions stored in D1.
- Discord client ID/secret from env/secrets.
- Mount Better Auth at `/api/auth/*`.
- Use `nodejs_compat` if required by the current Better Auth version.
- Secure cookies: HttpOnly, Secure in production, SameSite=Lax, Path=/.
- No session tokens in localStorage.

Discord application setup (document in README):

1. Discord Developer Portal -> Applications -> New Application.
2. OAuth2 -> add redirect:
   `https://<worker-subdomain>.workers.dev/api/auth/callback/discord`
   plus `http://localhost:8787/api/auth/callback/discord` for local dev.
3. Copy client ID and client secret. Never commit them.
4. No bot token, no bot permissions, no privileged intents.

Session middleware:

- `GET /api/me`: return `{ user: { id, name, image }, capacity }` or 401.
- Protected API routes: resolve session, 401 if absent.
- Mutations: verify same-origin (Origin/Sec-Fetch-Site) in addition to
  SameSite cookies.
- Never trust a user ID, destination ID, subscription ID, or role ID from the
  client without an ownership query.

Auth tests:

- Unauthenticated protected route -> 401.
- User A cannot read/update/delete user B's subscription or destination.
- Expired/invalid session -> 401.
- OAuth callback error -> friendly error, no secret leakage.
- Logout invalidates the session.
- Account deletion cascades user-owned data.

9. API CONTRACT
--------------------------------------------------------------------------------

All API routes are same-origin JSON under `/api`. Use Zod validation. Error
shape:

  { "error": { "code": "STRING_CODE", "message": "Human-safe message",
               "field": "optional" } }

Never include stack traces, SQL, webhook URLs, tokens, or secrets.

Public:

  GET /api/health
    -> 200 { ok: true, db: "ok" }
    -> 503 { ok: false, db: "error" }

  GET /api/status
    -> 200 {
         acceptingUsers: boolean,
         accountsUsed: number,
         accountsMax: number,
         activeSeries: number,
         activeSeriesMax: number
       }
    No personal data.

Authenticated:

  GET /api/me
    -> { user: { id, name, image }, capacity: {...}, waitlisted: boolean }

  POST /api/series/preview
    body { url: string }
    -> { series: {
           externalId, title, siteUrl, feedUrl,
           latest: { number, label, title, url, publishedAt }
         },
         alreadyTracked: boolean }

  POST /api/series
    body { url: string, destinationId: string }
    -> 201 { subscription: {...}, series: {...} }
    errors: CAPACITY_REACHED, SERIES_LIMIT, DESTINATION_LIMIT,
            SERIES_CAPACITY_REACHED, INVALID_SERIES_URL, FEED_UNAVAILABLE,
            DESTINATION_NOT_FOUND, SERIES_ALREADY_TRACKED

  GET /api/series
    -> { subscriptions: [
         { id, active, createdAt,
           series: { id, title, latestChapterNumber, latestChapterLabel,
                     latestChapterTitle, latestChapterUrl, lastCheckedAt,
                     nextCheckAt, lastError },
           destination: { id, label, status } }
       ] }

  PATCH /api/series/:subscriptionId
    body { active: boolean }
    -> { subscription: {...} }

  DELETE /api/series/:subscriptionId
    -> 204

  GET /api/destinations
    -> { destinations: [
         { id, label, status, guildName, channelName, roleId,
           lastError, lastCheckedAt, inUseBy: number }
       ] }
    Never return webhook_ciphertext/IV/fingerprint to the client.

  POST /api/destinations
    body { label: string, webhookUrl: string, roleId?: string }
    -> 201 { destination: {...} }
    Server GETs the webhook first; 400 if invalid/dead.

  PATCH /api/destinations/:id
    body { label?, webhookUrl?, roleId? }
    If webhookUrl is present, verify it, re-encrypt it, and reset status.
    -> { destination: {...} }

  DELETE /api/destinations/:id
    -> 204, or 409 DESTINATION_IN_USE

  POST /api/destinations/:id/test
    -> 200 { ok: true } or 502 { error: ... }
    Rate-limited. Sends a [TEST] embed. No state changes.

  GET /api/activity?limit=50&cursor=...
    -> { items: [
         { id, status, attempts, lastError, sentAt, createdAt,
           chapter: { number, label, title, url },
           series: { title },
           destination: { label } }
       ], nextCursor? }

  POST /api/account/delete
    body { confirm: "DELETE" }
    -> 204
    Delete the user and user-owned data. Shared series/chapters remain.

Do not add a public "run cron now" endpoint. For local tests, call the exported
scheduled handler directly. If you add a dev-only trigger, gate it behind
`ENVIRONMENT === "development"` and an explicit `DEV_CRON_SECRET`, and prove
it cannot run in production.

Rate limits to implement server-side:

- preview: 10/minute/user
- add/patch series: 30/minute/user
- add/patch destinations: 10/minute/user
- test send: MAX_TEST_SENDS_PER_HOUR per user/destination
- login: Better Auth's rate limiting plus Cloudflare-level protection if
  available. Do not build a fragile in-memory limiter; use D1 or an available
  binding.
  Return 429 with Retry-After.

10. WEEBCENTRAL SERIES INGESTION
--------------------------------------------------------------------------------

10.1 URL validation

Accept only:

  https://weebcentral.com/series/<id>
  https://weebcentral.com/series/<id>/<slug>
  https://www.weebcentral.com/series/<id>...
  an `/rss` variant of the above

Rules:

- HTTPS only.
- Host must be exactly `weebcentral.com` or `www.weebcentral.com`.
- No credentials in URL, no non-standard port, no fragment.
- Path must start with `/series/`.
- Extract `<id>` as the first path segment after `/series/`.
  IDs are alphanumeric; validate with `/^[A-Za-z0-9]+$/`.
- Normalize to:
    feedUrl = `https://weebcentral.com/series/${id}/rss`
    siteUrl = `https://weebcentral.com/series/${id}`
- Reject all other hosts. This is SSRF protection, not a convenience check.
- After fetch, if the response URL redirects off the allowlisted host, reject
  it. Do not follow arbitrary redirects.

10.2 Feed fetch

- `fetch(feedUrl, { headers: { "User-Agent": <current Chrome UA>,
  "Accept": "application/rss+xml, application/xml, text/xml" } })`
- Timeout 15 seconds via AbortController.
- Handle non-200: throw a typed `FeedError` with status.
- Parse XML with a proven parser. RSS shape:
    rss -> channel -> item[]
  Handle a single item being an object vs array.
- Required item fields: title, link.
- Extract chapter number with `/Chapter\s+(\d+(?:\.\d+)?)/i`.
  If it does not match, reject as unsupported feed; do not guess.
- Convert `"1089.5"` to 1089.5; `"1089"` to 1089.
- Keep the original title and URL.
- Read pubDate if present; otherwise empty.
- Store ETag/Last-Modified if available and send conditional headers next time.
- 304 Not Modified is a successful check; update last_checked_at, leave latest
  chapter unchanged.
- Never treat a fetch/parse error as "no new chapter". Surface it.

10.3 Preview

`POST /api/series/preview` must:

- validate URL;
- fetch/parse feed;
- return series metadata and latest chapter;
- not write to D1;
- rate-limit;
- return a friendly error for invalid/unsupported feeds.

10.4 Add series

- Re-validate URL on the server. Never trust the preview response.
- Upsert the global series by `(source, external_id)`.
- If it exists, reuse it; update title/feed/site only if safe.
- If it is new and `MAX_ACTIVE_SERIES` is reached, return
  `SERIES_CAPACITY_REACHED` unless the series already exists.
- Check the user's active series count.
- Check the destination belongs to the user and is active.
- Create subscription with `destination_id`.
- Set `next_check_at` to now + jitter, not immediately (avoid a thundering herd).
- No backfill. Do not create delivery rows for existing chapters.
- Record the subscription creation time; only chapters discovered after the
  subscription is active should notify it.

10.5 Series comparison

Use the same semantics as the reference:

- stored latest chapter is null/missing -> treat as new/missing;
- latest > stored -> new;
- latest == stored -> same;
- latest < stored -> older/reorder; ignore and keep state.

For a newly created series, set its baseline latest chapter from the preview so
existing chapters do not alert anyone. The next *new* chapter is the first alert.
This is important for a fresh subscription.

11. DESTINATIONS, ENCRYPTION, AND SSRF
--------------------------------------------------------------------------------

11.1 Discord webhook validation

Accept only HTTPS URLs that look like:

  https://discord.com/api/webhooks/<id>/<token>
  https://discordapp.com/api/webhooks/<id>/<token>
  https://canary.discord.com/api/webhooks/<id>/<token>
  https://ptb.discord.com/api/webhooks/<id>/<token>

Rules:

- HTTPS only.
- Host must be one of the allowlisted Discord hosts (or a discord.com subdomain
  if you explicitly allow it; never arbitrary hosts).
- Path segments must contain `webhooks` followed by at least two non-empty
  segments (id, token).
- No credentials in URL.
- Reject localhost, private IPs, metadata endpoints, `file:`, `data:`, etc.
  The allowlist is enough; do not add a generic URL fetcher.
- This validation is used for save, test, and delivery.

11.2 Verify on save

- GET the webhook URL with a 10s timeout.
- 200: parse JSON `{ name, channel_id, guild_id }`, optionally fetch channel/
  guild names if the webhook response includes them. Do not send a message.
- 401/403/404: reject as dead/unauthorized.
- 429/5xx: reject with a retryable message; do not save a broken destination.
- Store only display metadata (guild/channel names), ciphertext, IV, and a
  SHA-256 fingerprint for duplicate detection.

11.3 Encryption

- Master key: `WEBHOOK_ENCRYPTION_KEY`, base64-encoded 32 random bytes, stored
  as a Worker secret.
- Generate a random 12-byte IV per encryption.
- AES-256-GCM via `crypto.subtle`.
- Store base64 ciphertext and base64 IV separately.
- Prefix a version, e.g. `v1`, to support future key rotation.
- Never return plaintext to the client after save.
- Never log plaintext or full ciphertext.
- Decrypt only inside the Worker, immediately before a send/test.
- Duplicate detection uses SHA-256 of the URL per user, not the URL itself.
- If decryption fails, mark the destination `disabled` and show "Re-add this
  webhook" in the UI. Do not crash the whole cron.

11.4 Role IDs

- Optional. Empty/whitespace means no ping.
- If provided, accept a bare numeric Discord snowflake (17–20 digits) or a
  `<@&123...>` mention; normalize to bare digits.
- Invalid non-empty input -> 400 validation error, not a silent omission.
- Payload:
    content: `<@&ROLE_ID>`
    allowed_mentions: { parse: [], roles: [ROLE_ID] }
- Without a role ID, omit both fields.
- Explain in the UI that the role must be mentionable in Discord for a push
  notification to reach members.
- We cannot verify role membership without a bot; do not fake it.

11.5 Webhook status

- `active`: normal.
- `disabled`: permanent 401/403/404 or decryption failure.
- On disable, stop retrying and show a banner on Destinations and Activity.
- A successful test or replacement re-enables.
- Do not delete the destination automatically; the user may want to fix it.

11.6 Test send

- Server-side only.
- Uses the real Discord POST path.
- Payload title starts with `[TEST]`, description says it is not a new chapter.
- Includes the role ping if configured.
- Does not create chapters/deliveries, does not change series state.
- Rate-limited.
- Returns a safe error message on failure.

12. SCHEDULER AND DELIVERY ENGINE
--------------------------------------------------------------------------------

12.1 Cron

- One Cron Trigger: `*/5 * * * *` (every 5 minutes).
- The Worker's `scheduled()` handler:
  1. acquire a lock;
  2. poll due series in a bounded batch;
  3. process due deliveries in a bounded batch;
  4. release lock;
  5. record a job_runs row.

Locking:

- `job_locks` table with name `poll` and `locked_until`.
- Atomically claim only if `locked_until < now`; set to now + 4 minutes.
- If another run holds it, log and return. Never run two pollers concurrently.
- Release/clear the lock in a finally block if possible. If the Worker dies,
  the lease expires.

12.2 Feed polling

Select due series:

  SELECT ...
  FROM series s
  WHERE s.active = 1
    AND s.next_check_at <= :now
    AND EXISTS (
      SELECT 1 FROM subscriptions sub
      WHERE sub.series_id = s.id AND sub.active = 1
    )
  ORDER BY s.next_check_at
  LIMIT CRON_BATCH_SERIES

For each:

- Before fetching, set next_check_at = now + POLL_INTERVAL_MINUTES + jitter
  (e.g. 0–5 min) so a failure does not cause an immediate retry loop.
- Fetch with conditional headers.
- 304: update last_checked_at, clear transient error, continue.
- 200: parse. If no valid chapter, set last_error and schedule a sooner retry
  (e.g. 10 min) without advancing state.
- If chapter > stored latest:
  - insert chapter row; unique constraint protects against races;
  - update series latest fields;
  - create delivery rows for every active subscription of this series.
- If chapter == stored: update check time, clear transient error.
- If chapter < stored: log a warning, do not advance state.
- If series has no subscribers: set active = 0 or skip; do not poll forever.
- Do not poll the same series twice in one run.

Fanout:

- For each active subscription, create a delivery row for the chapter/destination.
- Use `INSERT OR IGNORE` / unique `(chapter_id, destination_id)`.
- Do not create deliveries for subscriptions created after the chapter was
  discovered. A subscription should only receive chapters found while it is
  active; no backfill.
- Cap deliveries per run; leave the rest queued.

12.3 Delivery

Select due deliveries:

  status IN ('pending', 'retry')
  AND next_attempt_at <= now
  ORDER BY next_attempt_at
  LIMIT CRON_BATCH_DELIVERIES

For each:

- Load destination. If disabled, mark skipped and continue.
- Decrypt URL. If decryption fails, disable destination, mark failed.
- Build payload:
    title: series title + chapter label
    url: chapter URL
    description: "A new chapter of <series> is out."
    color: vermilion/orange
    timestamp: now
    footer: "Chapter Tracker"
    role content/allowed_mentions if configured.
- POST with 15s timeout.
- 200/204 -> `sent`, sent_at = now, attempts += 1, clear error.
- 429 -> `retry`, use Retry-After if present; cap delay; schedule next attempt.
- 5xx/network/timeout -> `retry`, exponential backoff (e.g. 1, 5, 15, 60
  minutes with jitter), attempts += 1.
- 401/403/404 -> `failed`, disable destination, save sanitized error.
- Malformed URL -> `failed`, disable destination.
- After max attempts (e.g. 5), mark `failed` but keep the row for the activity
  log. Do not retry forever.
- Never re-send a delivery already marked `sent`.
- A destination that succeeded in an earlier run is never notified again for
  that chapter.
- Do not claim exactly-once; document the ambiguous-network caveat.

Rate limits:

- Discord webhook limits are per webhook. Send sequentially or with very low
  concurrency. Honor 429 Retry-After.
- Keep the cron batch small. Do not parallelize 20 POSTs without need; sequential
  is safer and still fast enough.

12.4 Cleanup

- Delete job_runs older than 30 days.
- Delete deliveries older than 90 days? Keep activity for 30 days; align.
- Delete sent/failed deliveries older than 30 days.
- Do not delete series/chapters that have active subscriptions.
- Delete orphan series with no subscriptions after a grace period, or set
  inactive. Keep it simple: leave them, but do not poll them.

12.5 Status and capacity

- `GET /api/status` returns remaining capacity.
- UI shows "Next check in ~X minutes" based on next_check_at; under backlog it
  may be later. Label it approximate.
- A "capacity reached" state must be explicit and must not look like a bug.
- If D1/Worker returns quota errors, show a service-unavailable state and log
  safely. Do not retry in a tight loop.

12.6 Pseudo-code

  scheduled(event, env, ctx) {
    if (!await acquireLock(env.DB, "poll", 4 minutes)) return;
    try {
      const run = await startJobRun(env.DB);
      const series = await selectDueSeries(env.DB, MAX_ACTIVE_SERIES, now);
      for (const s of series) {
        await markNextCheck(env.DB, s.id, now);
        try {
          const feed = await fetchFeed(s.feed_url, s.etag, s.last_modified);
          if (feed.notModified) continue;
          const chapter = parseLatestChapter(feed);
          if (isNew(s, chapter)) {
            await recordChapterAndQueueDeliveries(env.DB, s, chapter);
          }
        } catch (err) {
          await recordSeriesError(env.DB, s.id, safeError(err));
        }
      }
      const due = await selectDueDeliveries(env.DB, 20, now);
      for (const d of due) await deliverOne(env.DB, d);
      await finishJobRun(...);
    } finally {
      await releaseLock(env.DB, "poll");
    }
  }

13. SECURITY, PRIVACY, AND ABUSE
--------------------------------------------------------------------------------

13.1 Secrets

Worker secrets:

  BETTER_AUTH_SECRET          long random string
  DISCORD_CLIENT_SECRET       Discord OAuth app secret
  WEBHOOK_ENCRYPTION_KEY      base64 32-byte key
  DEV_CRON_SECRET             optional, dev only; never production

Public vars:

  APP_URL                     exact public origin
  DISCORD_CLIENT_ID           public OAuth client ID
  MAX_ACCOUNTS
  MAX_SERIES_PER_USER
  MAX_DESTINATIONS_PER_USER
  MAX_ACTIVE_SERIES
  POLL_INTERVAL_MINUTES
  CRON_BATCH_SERIES
  CRON_BATCH_DELIVERIES
  MAX_TEST_SENDS_PER_HOUR

Never expose secrets to the client. Vite only exposes `VITE_*` variables; do
not put secrets in them. Check the built bundle for accidental secret names.

13.2 Authorization

- Every user-owned query must include user_id ownership.
- Never accept a destination_id/series_id/subscription_id without verifying it
  belongs to the session user.
- Return 404 (not 403) for another user's resource to avoid enumeration.
- Deleting a destination in use returns 409.
- Adding a subscription with another user's destination is impossible.
- Tests must prove user A cannot affect user B.

13.3 CSRF / same-origin

- Same-origin SPA and API; no wildcard CORS.
- Cookies HttpOnly, Secure (production), SameSite=Lax.
- Mutation routes verify Origin/Sec-Fetch-Site.
- Better Auth handles OAuth state. Do not implement your own OAuth state.
- Post-login return path must be a local path only; reject `//evil.com`.

13.4 SSRF

- Only exact weebcentral hosts for feeds.
- Only allowlisted Discord hosts for webhooks.
- No generic proxy/fetch endpoint.
- Reject redirects off the allowlist.
- Do not allow private IPs, localhost, metadata services, or file/data URLs.
- Keep timeouts.

13.5 XSS / headers

- React escapes by default; no `dangerouslySetInnerHTML`.
- No user HTML in embeds or UI.
- Set security headers: CSP, X-Content-Type-Options, Referrer-Policy,
  Permissions-Policy, frame-ancestors 'none', HSTS in production.
- Content Security Policy must allow your static assets/fonts; do not add
  `unsafe-eval` in production.
- Use HTTPS only.

13.6 Abuse

- Account cap, per-user caps, preview/edit/test rate limits.
- Webhook URLs are secrets; never display them after save.
- A user can still spam their own webhook via test sends; rate-limit.
- No public unauthenticated write endpoints.
- Monitor job_runs; a single series with a failing feed should not block all.
- Keep logs free of URLs, tokens, cookies, Discord IDs beyond what is necessary.
- Do not add analytics in v1.

13.7 Privacy

- Data: Discord ID/name/avatar, session data, series subscriptions, encrypted
  webhook URLs, role IDs, delivery metadata, waitlist entry.
- Purpose: deliver chapter alerts and operate the service.
- Storage: Cloudflare D1; encrypted at rest by Cloudflare, plus app-level
  encryption for webhook URLs.
- Retention: activity/job logs 30 days; account data until deletion; waitlist
  until capacity opens or 90 days.
- Account deletion: delete user, sessions, subscriptions, destinations,
  deliveries, waitlist entry; shared series/chapters remain.
- No sale of data; no third-party analytics; no marketing email.
- Essential cookies only. No cookie banner unless legally required; document.
- Contact placeholder in PRIVACY.md; tell the operator to fill it.
- Not affiliated with Discord or weebcentral.

13.8 Legal/content

- Store only chapter metadata and links from RSS; do not host chapter pages or
  images.
- Link users to weebcentral for the chapter.
- Respect weebcentral's terms/robots and rate limits.
- Do not bypass paywalls, authentication, or anti-bot protections.
- If the feed disappears or terms change, surface an error and document it.
- Terms are a draft; operator must review.

15. TESTING PLAN
--------------------------------------------------------------------------------

15.1 Unit tests

- Weebcentral URL parse: valid ID/slug, `/rss`, optional www, query, invalid
  host, other path, credentials, port, fragment, SSRF attempts.
- RSS parser: one item, item array, missing title/link, malformed XML, title
  without "Chapter", decimal chapter, HTML entities.
- Chapter compare: missing/new/same/older.
- Chapter label normalization.
- Role ID: blank, numeric, full mention, invalid, injection-ish strings.
- Webhook validation: valid Discord hosts/paths, http, arbitrary host,
  localhost, private IP, short path.
- Encryption: round trip, random IV, tamper detection, wrong key fails,
  ciphertext contains no plaintext.
- Capacity: account/series/destination/global caps; race-like sequential
  checks; existing series reuse.
- Retry classification: 401/403/404 permanent, 429/5xx/network transient,
  Retry-After parsing, max attempts.
- Payload builder: no role -> no content/allowed_mentions; role -> exact
  content and roles array; test marker.
- Error sanitization: no URL/token in messages.

15.2 Worker/D1 integration tests

Use @cloudflare/vitest-pool-workers or Miniflare and a real local D1:

- migrate schema;
- create two users;
- add destination for A; B cannot see/update/delete it;
- add series/preview with mocked `fetch`;
- subscription routes; cap enforcement;
- feed poll creates chapter and deliveries once;
- second poll does not duplicate;
- failed destination retries; successful destination is not re-sent;
- 404 disables destination; replacement re-enables;
- 429/timeout schedules retry;
- role payload only for configured destination;
- test send writes no state;
- activity is user-scoped;
- account deletion cascades;
- waitlist at account cap;
- cron lock prevents overlap;
- batch limits respected;
- cleanup deletes old rows.

Mock all outbound `fetch`. Never call real Discord or weebcentral in tests.
Keep XML fixtures small and checked in.

- landing/login redirect (mock OAuth or a dev-only test session; never a
